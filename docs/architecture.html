The Personal CRM

How the whole system works, from Signal message to profile page

Architecture guide · July 2026

What this is A system that reads your Signal conversations once a day, and for each person you care about, maintains a living document about them: who they are, what's going on in their life, what you should ask them about next time you talk, and a full history of your conversations — with every claim traceable back to the exact message it came from. You read the results in a small private web app.

1. The big picture

The system has three moving parts that run once a day, in order, plus a web app you can open any time:

  • Refresh — reads Signal's local message database and collects everything new since the last successful run, per person.
  • Merge — hands each person's new messages to an AI model (Claude Opus 5), which updates that person's profile document: new facts, updated talking points, resolved open questions.
  • Compaction — maintains each profile's conversation timeline, keeping recent history verbatim and progressively summarizing older history so profiles never grow without bound.
  • Web app — a password-protected page on your own machine where you browse the profiles, see what to bring up with each person, and click any claim to see the original message that backs it.
Figure 1 — The whole system. Signal is only ever read, never written.

Two properties shape almost every design choice in the system:

It must never lose a message. If anything crashes partway through — the machine sleeps, the model errors, the power goes out — the next run must pick up exactly where the last successful work left off. Messages can be processed twice (that's harmless, as you'll see), but never skipped.

It must never invent a memory. An AI model summarizes your conversations, and models can hallucinate. The provenance system (section 8) exists so that anything important the model writes carries a pointer to the real message behind it, and a validator checks those pointers actually exist.

2. The three stores of data

Data lives in three places, each chosen for what it's good at:

StoreWhat it holdsWhy this form
Signal's own database Every message, exactly as Signal Desktop stores it. Encrypted. Not ours — we treat it as a read-only source of truth and never modify it.
The CRM database (a single SQLite file, crm.db) The contact registry (who is tracked, their Signal identity, when you last talked) and the message archive — a permanent copy of every message the pipeline has ever processed. Messages are structured, immutable records — exactly what a database is for. The archive also makes provenance durable: even if Signal purges old messages, the citations in profiles still resolve.
Profile documents (one Markdown file per person) The narrative: who they are, what you know about them, talking points, open questions, and the timeline. Profiles are prose that an AI edits daily and a human reads. Plain text is easy for the model to edit surgically, easy to diff to see what changed, and readable with any tool. A database row would make all three harder.

This hybrid split — structured facts in SQLite, narrative in Markdown — was a deliberate decision. An earlier question was whether to move everything into SQLite. The answer was no: forcing the model to edit prose stored inside database fields would make the daily merge brittle and the history opaque, without making citations any more trustworthy. Instead, each store does what it's best at, and citations bridge the two.

Anatomy of a profile

Every person's profile document has the same sections, and — importantly — different parts of the system own different sections. The merge and compaction steps are forbidden from touching each other's territory, which is what lets them run independently without corrupting each other's work:

What I knowStable facts: where they live, what they do, family, preferences, history. Clean prose, no citations.Merge (AI)

3. Getting messages out of Signal

Signal Desktop keeps all messages in an encrypted SQLite database on your machine. The encryption key is itself stored encrypted, protected by Windows' built-in DPAPI (the same mechanism browsers use to protect saved passwords — it can only be unlocked by your Windows user account on this machine).

At startup, the pipeline unwraps that key the same way Signal itself does — DPAPI to recover a wrapping key, then one more decryption step to recover the database key — and opens the database read-only. A previously-derived key is kept as a fallback so a run doesn't fail if the derivation path changes; if Signal ever rotates the key, the system re-derives it.

Boundary rule The system never writes to Signal's database, never sends messages, and never talks to Signal's servers. It is a passive reader of the local copy of conversations that Signal Desktop already syncs to your machine.

Identity

Signal identifies every account by a stable random ID (a "service ID") rather than a phone number. The system knows two special IDs: yours (so it can tell which messages you sent — important in group chats, where the message's type alone doesn't say who spoke) and the old bot's (a previous automation account that still sits in some group chats; its messages are filtered out everywhere, and it never counts as a "person" when deciding what kind of conversation a chat is).

4. What counts as "a conversation with this person"

This is one of the subtler parts of the system, and it exists because of a real problem: some people you barely message 1:1 at all. Katia, for example, is talked to almost entirely inside a two-person group chat — so a naive "read the DM" approach saw almost nothing of the relationship.

For each tracked person, the system therefore classifies every conversation they appear in into one of three kinds, and takes different messages from each:

Figure 2 — Source classification, applied identically everywhere messages are gathered.

The reasoning behind each rule:

  • DMs are unambiguous — everything in them is part of the relationship.
  • Bi-groups (like "Nat & Kat") are private channels in disguise. They're technically group chats, but the only two humans in them are you and the contact, so both directions belong in their history.
  • Multi-groups are shared spaces. Importing everything from a 12-person group into one person's profile would flood it with other people's words. So the profile only captures what that person said there — enough to know what's going on in their life without absorbing the whole group.

Crucially, this classification lives in one shared piece of logic used by both the refresh step and the compaction step. That matters because the two run at different times over different windows — if they each had their own idea of which conversations count, the daily updates and the long-term timeline would silently disagree about what was said. (This was an actual bug: compaction originally looked only at DMs, so Katia's timeline claimed "no messages this week" while nine hundred group messages sat unread.)

5. The daily pipeline, step by step

An orchestrator script runs the whole sequence nightly (and can be run by hand, including in a dry-run mode that reports what it would do without calling the model or changing anything).

Figure 3 — One nightly run. The cursor for a person moves only after their merge succeeds.

Cursors: how "new since last time" is tracked without losing anything

Each person has a cursor: a bookmark recording the last message that was successfully merged into their profile. The refresh step reads everything past the bookmark; the orchestrator advances the bookmark only after that person's merge has actually succeeded.

The bookmark is deliberately not a timestamp. Message timestamps are set by the sender's clock, which can be skewed, and Signal's device sync can insert older messages into the database long after they were sent. A timestamp watermark can therefore silently skip messages that arrive "in the past." Instead, the cursor is the database's own insertion counter — a number that only ever increases as rows land in your local database, regardless of when the message claims to have been sent. Anything that arrives after the last run has a higher number than the bookmark, full stop.

Crash safety The refresh step itself never saves cursors — it only proposes them. If the machine dies mid-run, or the model fails on person #4 of 10, persons 1–3 keep their advanced cursors and persons 4–10 keep their old ones. The next run simply re-pulls the unmerged messages and tries again. The worst case is duplicated work, never a lost message — and the profile merge is written to tolerate seeing the same messages twice.

New contacts and backfill

The system keeps a small tracked list of people. It also watches for anyone you've been messaging frequently who isn't tracked yet and promotes them automatically. A newly tracked person has no cursor, so their first refresh does a 30-day backfill: it pulls the last month of history by date to give the model enough context to write a meaningful first profile, and the cursor takes over from there.

The ledger

The refresh step's output for each person is a ledger: a plain-text transcript of their new messages, one per line, with a timestamp, the message's permanent ID (more on this in section 8), the group name if it came from a group, the speaker, and the text:

[2026-07-19 22:41] ⟨m84810⟩ (Nat & Kat 🥾🩷) Katia: ok I found the espresso machine I want [2026-07-19 22:41] ⟨m84811⟩ (Nat & Kat 🥾🩷) Katia: the breville one, it's on sale [2026-07-19 22:43] ⟨m84815⟩ (Nat & Kat 🥾🩷) Nathan: get it!!

This is exactly what the AI model sees during the merge — nothing more, nothing less.

6. The merge: why an AI agent edits the profiles

The merge is the intelligent step: take one person's ledger of new messages and fold it into their profile. That means deciding what's a durable fact ("she's moving in with Rori in the fall") versus noise ("lol"), updating talking points, deleting stale ones, and resolving open questions — all while leaving the rest of the document, especially the Timeline, untouched.

Why not just call a summarization API?

Because the job isn't "summarize this text" — it's "make a careful, minimal edit to an existing document." Asking a model to regenerate the whole profile from scratch every day would slowly mangle it: details drift, phrasing churns, and sections the model shouldn't touch get rewritten anyway. What's needed is a model that can read the current profile, decide what changed, and apply surgical edits — which requires a tool-using loop around the model, not a single API call.

Rather than building that loop from scratch, the system uses pi, a small headless coding-agent harness, as the wrapper. It contributes three things:

  • The read/edit loop — the model can open the profile, search it, and patch specific lines, instead of regenerating the file.
  • Subscription authentication — model calls go through your existing Claude subscription rather than a separately billed API key.
  • Model agnosticism — the model is one configuration string. The pipeline ran on a completely different provider's model before switching to Claude Opus 5, with no code changes. This was an explicit design requirement.

The rules the model works under

The merge prompt gives the model a strict contract, and the important clauses are:

  • It owns What I know, Talking points, and Open questions — and must leave the Timeline byte-for-byte untouched.
  • Talking points must be dated, specific, and actionable ("ask if the espresso machine arrived", not "coffee"), capped at roughly eight, with stale ones deleted, and each must end with 1–3 source-message IDs copied exactly from the ledger — never invented, omitted if unsure.
  • What I know and Open questions stay clean prose with no citations — a deliberate choice to keep the readable narrative readable.

After every merge, the orchestrator independently checks every citation the model wrote against the message archive. A citation pointing at a message that doesn't exist is flagged as a probable hallucination and logged as a warning. This check is the safety net that makes it reasonable to trust the talking points.

7. The timeline and compaction: remembering at the right resolution

If profiles simply accumulated every message forever, they would become unreadable within weeks and far too large for the model to process. But throwing history away isn't acceptable either. Compaction resolves this the way human memory does: recent things in full detail, older things as summaries, ancient things as a few lines.

Figure 4 — The resolution gradient. Every night, content slides one notch left-to-right as it ages.

Each night, compaction recomputes which messages fall into which tier and rewrites the Timeline section accordingly. Messages crossing a tier boundary get summarized by the model (a plain summarization call — this step doesn't need the editing loop). Summaries are asked to cite the handful of messages that carry the day's real content — a plan made, a date mentioned, news shared — so even a one-line summary of a week from two months ago remains clickable back to sources.

Groups in the timeline

Timelines draw from the same three-way source classification as refresh, interleaving DM and group messages into one chronological stream (each line tagged with where it happened). Larger group chats also get their own summaries, which fold a one-line digest into each member's profile ("group activity"). Two-person bi-groups are excluded from that folding — their content is already fully present in the person's own timeline, and including them twice would duplicate everything.

8. Provenance: every claim traceable to a real message

This is the newest layer of the system, and it answers one question: "where did that come from?" — for any talking point or timeline summary, you can get back to the exact message behind it, in context.

It works in four stages:

Figure 5 — The provenance chain, from Signal message to clickable citation.
  1. Stable IDs. Every message already has a permanent number in the local database — the same number the cursors use. That number becomes the message's citation ID for life.
  2. Archival. Every message the pipeline touches is copied into the CRM database's archive (idempotently — seeing it twice changes nothing). This makes citations durable: they don't break if Signal's own database ever trims old history.
  3. Citation. Ledger and timeline lines carry their IDs inline, and the model is instructed to copy the relevant ones — exactly, never invented — onto talking points and summaries. Citations deliberately appear only on Talking points and the Timeline; the narrative sections stay clean.
  4. Verification and viewing. After each merge, every cited ID is checked against the archive. In the web app, citations render as small superscript numbers; clicking one opens the original message highlighted in the middle of its surrounding conversation.
Why this design is trustworthy The model never generates an ID — it can only copy IDs that were present in the text it was shown, and an independent check catches any it makes up. The archive the citations resolve against is written by plain code during refresh, before the model is ever involved. So a citation that validates is a real message, guaranteed.

9. Talking points and the radar: the "good listener" layer

The most practically useful output of the system is the Talking points section of each profile: a short, dated list of things worth bringing up with that person — a plan they mentioned, something they were excited about, a date coming up, a thing they said they'd do that you can ask about. The model maintains it daily: adding new items from fresh messages, sharpening phrasing into something actionable, and deleting anything stale or resolved.

The web app's home page aggregates these across everyone into a radar panel — "things to bring up" — ordered so the most time-sensitive items surface first: upcoming dated items soonest-first, then recent mentions newest-first, then undated items, capped so no one person floods the list. Each item links to its person, and its citation links to the originating message.

10. The web app

A small, dependency-free web server runs on your machine only (it binds to localhost and is not reachable from the network). Everything is behind a username/password, checked with constant-time comparison. Serving it on a real domain was considered and deliberately deferred — local-only for now.

11. Design decisions and why they were made

DecisionAlternative rejectedWhy
Per-person insertion-order cursors One global timestamp watermark Sender clocks skew and synced messages arrive late; a timestamp watermark silently skips them. Insertion order can't.
Cursors commit only after a successful merge Refresh saves its own progress A crash between refresh and merge would otherwise lose messages forever. Re-processing is safe; skipping is not.
Hybrid storage: SQLite archive + Markdown profiles Everything in SQLite, or everything in text files Messages are immutable records (database strength); profiles are AI-edited, human-read prose (plain-text strength). Each store does what it's good at; citations bridge them.
DM + bi-group + multi-group source rules, in one shared module DMs only, or per-script logic Some relationships live almost entirely in group chats; and if refresh and compaction classified sources differently, daily updates and the timeline would quietly diverge.
An agent harness (pi) around the model A raw "summarize this" API call The job is surgical document editing, not summarization. The harness supplies the read/edit tool loop, subscription auth, and one-string model swapping.
Citations only on Talking points and Timeline Citations on everything Your call: the narrative sections should read as clean prose. Citations go where claims are actionable or time-bound — where "where did that come from?" actually gets asked.
Section ownership: merge vs. compaction One process owns the whole file Two independent writers of one document need hard boundaries. The merge may not touch the Timeline; compaction touches nothing else. Neither can corrupt the other's work.
Strict resolution gradient in timelines Keep everything, or keep a fixed window Full history is unreadable and too big for the model; a fixed window forgets. Graded summarization keeps profiles small, current, and still historically deep.
